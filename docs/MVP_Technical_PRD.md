## 1. Document Purpose

This document defines the technical product requirements for the MVP of a prompt-to-ad video generator.

The MVP goal is to let a user enter a prompt, configure a small set of parameters, optionally provide product links or uploaded assets, and receive a rendered short-form social ad with:

- AI-generated script
- AI-generated or selected visuals
- generated video with embedded speech/audio
- auto-synced subtitles
- exported video ready to post on social media

This PRD is limited to the **development-phase MVP scope**. It excludes advanced collaboration, marketplaces, avatars, complex editing suites, enterprise governance, and broad automation workflows.

---

## 2. Product Summary

### 2.1 Problem Statement

Teams want ready-to-publish short-form ads without needing separate tools for copywriting, subtitle timing, asset sourcing, and video editing.

Current workflows are fragmented:

1. write copy manually
2. source visuals manually
3. generate video and speech separately from the edit workflow
4. create subtitles separately
5. assemble video in an editor
6. export in platform-specific formats

The MVP must compress this into a single guided workflow.

### 2.2 MVP Value Proposition

A user can:

1. type a prompt
2. choose ad parameters
3. optionally provide product details and links
4. generate a social-ready ad video with synced subtitles

### 2.3 Primary MVP Use Case

**Prompt -> brief -> script -> assets -> Veo 3.1 (video) + script-derived subtitles -> render -> export**

### 2.4 Current Implementation Slice

The first delivery slice of the MVP shall implement a narrower end-to-end flow focused on prompt-to-video generation only:

**Prompt -> async job creation -> Vertex AI video generation -> GCS storage -> signed URL delivery -> frontend playback**

This slice is intentionally narrower than the full MVP scope and defers final social render composition to later steps. Video is generated by Veo 3.1; subtitles are derived algorithmically from the script.

## 3. Goals and Non-Goals

### 3.1 Goals

The MVP must:

- accept prompt-based ad generation requests
- accept structured product information
- optionally scrape product URLs for enrichment
- generate a script suitable for short-form ads
- generate or select visuals for each scene
- generate video with embedded speech/audio
- generate synchronized subtitles from script timing
- support chunk-level subtitle highlighting
- compose and render a vertical social video
- export an MP4 ready for social posting
- support regeneration of the full ad or individual scenes

### 3.2 Non-Goals

The MVP will **not** include:

- AI avatars
- team collaboration features
- template marketplace
- deep timeline editing UI
- multi-user permissions
- campaign analytics
- A/B testing dashboards
- ad account publishing integrations
- full brand-kit management suite
- long-form horizontal video workflows
- enterprise approval flows
- full white-label API platform

### 3.3 Current Delivery Slice Constraints

For the current implementation milestone, the system will **not yet** implement:

- final caption burn-in
- script/scene regeneration
- persistent job queue infrastructure
- database-backed job persistence

If a URL is provided, the system shall:

2. extract structured product information where possible
3. detect available assets
4. normalize extracted content into a common internal schema

### Extraction Targets
- product name

- benefits

- media URLs
- CTA text if visible
- brand colors if detectable

If scraping fails:
- continue with manual user input only

## 7.4 Script Generation

The system shall generate a short-form ad script optimized for social media video.

### Script Requirements
- strong opening hook
- concise body
- clear CTA
- scene-by-scene narration chunks
- subtitle-friendly sentence lengths
- output duration should fit requested duration target

### Script Outputs
```json
{
  "title": "",
  "hook": "",
  "narration_lines": [
    {"scene": 1, "text": ""},
    {"scene": 2, "text": ""}
  ],
  "cta": ""
}
```

### MVP Generation Variants
- generate 1 primary ad by default
- architecture should permit future support for 3 variants without redesign

## 7.6 Asset Layer

The system shall support the following asset sources for MVP:

1. uploaded user images/videos
2. stock media provider
3. generated images
4. optional generated video scenes for selected scene types only

### Prioritization Logic
1. user-uploaded brand/product assets
2. scraped product media
3. stock media
4. generated visual fallback

### Asset Constraints
- all selected assets must match aspect ratio strategy or be crop-safe
- all assets must be downloadable/accessible to render workers
- unsupported or missing assets must not block the job if fallback is available

## 7.7 Veo 3.1 Video Output

The system shall utilize Veo 3.1 to generate the video with embedded speech. Veo does **not** provide subtitle data — subtitles are generated separately from the script.

### Requirements
- Veo 3.1 generation shall provide the source video storage key and actual video duration.
- Subtitle generation is handled separately by the script-derived subtitle generator.

### Output Schema (partial)
```json
{
  "output": {
    "videoStorageKey": "...",
    "sourceVideoStorageKey": "...",
    "durationSec": 28.5
  }
}
```

---

## 7.8 Script-Derived Subtitle Generation

The system shall algorithmically generate subtitle timing from the `AdScript` and `ScenePlan[]` artifacts. This runs in parallel with Veo video generation.

### Subtitle Requirements
- subtitles must align to the script's planned scene durations, with post-correction scaling after Veo returns actual video duration
- subtitles must be chunked at 3-4 words per display for readability
- maximum 2 lines on screen at once
- support style presets
- support safe vertical placement for social UIs
- support active-chunk highlighting during playback
- burn subtitles into final export in MVP

### Subtitle Chunking Rules
- target 3-4 words per chunk
- phrase-aware line breaking at punctuation
- minimum 0.8 seconds display duration per chunk
- avoid orphan single-word chunks
- punctuation-aware splitting

### Subtitle Output Schema
```json
[
  {
    "start": 0.42,
    "end": 1.45,
    "text": "Creating ad videos",
    "scene_id": 1
  },
  {
    "start": 1.46,
    "end": 2.35,
    "text": "should not take days.",
    "scene_id": 1
  }
]
```

### Post-Correction Scaling
After Veo returns actual video duration:
```
corrected_timestamp = original_timestamp × (actual_duration / planned_duration)
```

### MVP Subtitle Styles
- standard bold caption
- kinetic highlight caption

---

## 7.9 Video Composition and Rendering

The system shall compose the final ad into an MP4 suitable for social posting.

### Composition Requirements
- vertical 9:16 timeline support
- preserve and mix generated speech/audio track
- subtitle burn-in
- animated Remotion captions with active-chunk highlighting
- background music at lower volume than speech
- transitions between scenes
- CTA overlay on final scene
- export with platform-safe margins

### Render Output Requirements
- final MP4
- thumbnail image
- transcript JSON
- subtitle JSON or SRT
- scene metadata

### Render States
- queued
- processing
- rendering
- completed
- failed

### Current Delivery Slice States
- queued
- processing
- completed
- failed

## 8. Recommended Technical Approach

## 8.1 Architecture Overview

The MVP shall use an asynchronous pipeline architecture.

```text
Client App
  -> API Backend
  -> Job Queue
  -> Pipeline Workers
      -> Scraping service
      -> LLM service
      -> Asset service
      -> Asset service
      -> Veo 3.1 Generation Service
      -> Script-derived subtitle generator (parallel with Veo)
      -> Render service
  -> Object Storage
  -> Database
```

### Current Delivery Slice Architecture

```text
Frontend
  -> Backend API
  -> In-memory Job Store
  -> Vertex AI Video Generation Service
  -> GCS Storage Service
  -> Signed URL Response
  -> Frontend Video Playback
```

## 8.2 Recommended Components

### Backend API
- FastAPI or NestJS

### Database
- PostgreSQL

### Queue / Jobs
- Redis + BullMQ / RQ / Celery equivalent

### Storage
- EU object storage for source and rendered files
- backend-managed GCS bucket access using Firebase/GCP service-account credentials
- short-lived signed URL delivery to frontend clients

### Rendering
- Remotion for composition layer

### AI Services
- LLM provider for brief/script generation
- Veo 3.1 for video generation
- optional video/image generation provider
- optional stock media provider

### Current Delivery Slice Service Use
- Vertex AI Veo generation is required
- GCS storage is required
- backend service-account-based upload/signing is required
- transcription, alignment, and rendering services are deferred for this slice

## 9. Suggested External Service Roles

The implementation should keep vendors abstracted behind internal interfaces.

### Service Adapter Interfaces
- `ScraperAdapter`
- `LLMAdapter`
- `StockMediaAdapter`
- `ImageGenerationAdapter`
- `VideoGenerationAdapter` (Veo 3.1)
- `RendererAdapter`

This prevents hard vendor lock-in and supports replacement during compliance, cost, or quality changes.

## 10. System Workflow

## 10.1 End-to-End Pipeline

```text
1. User submits ad request
2. Request is validated and stored
3. URLs are scraped if present
4. Product data is normalized
5. Creative brief is generated
6. Script is generated
7. Scenes are planned
8. Assets are collected/generated
9. Video generated via Veo 3.1; Subtitles generated from script (parallel)
10. Timeline JSON is built
12. Render worker exports video
13. Final artifacts are stored
14. Client receives completed result
```

## 10.2 Stage Model

Each job shall have explicit stage statuses:

```text
created
-> scrape_ready
-> brief_ready
-> script_ready
-> assets_ready
-> veo_output_ready
-> composition_ready
-> rendering
-> completed
```

### Failure Model
If a stage fails:
- job status becomes `failed`
- failing stage is recorded
- retry may resume from last successful stage

## 15. Quality Requirements

## 15.1 Output Quality Bar
A generated ad is considered acceptable if:
- subtitles are readable and synchronized
- narration fits duration target
- scenes roughly align with narration meaning
- final video has no black frames or missing media
- text overlays remain within safe area

## 17. Risks and Mitigations

| Risk | Description | Mitigation |
|---|---|---|
| Scraping inconsistency | Product pages vary widely | Normalize extracted data and keep manual inputs authoritative |
| TTS timing mismatch | Provider timestamps may be imperfect | Add alignment fallback layer |
| Generative video instability | Text-to-video may be slow or visually inconsistent | Use stock/uploaded assets as primary path |
| Render complexity | Subtitle and motion layering can fail | Use explicit timeline schema and validation |
| Vendor lock-in | Critical capabilities tied to one provider | Use internal adapter interfaces |
| Cost spikes | Media generation and rendering can become expensive | Limit generated-video usage in MVP |
| Long job times | Users may drop if processing is opaque | Provide stage-based progress and async delivery |

## 20. Recommended MVP Build Decision

For the MVP, the most practical implementation strategy is:

- asynchronous pipeline backend
- product URL scraping as optional enrichment
- LLM-generated brief/script
- uploaded assets + stock media as primary visual path
- optional generated scenes only where beneficial
- TTS with timing metadata
- subtitle post-processing for readability
- renderer-controlled final export with burned captions

This approach minimizes instability while maximizing the probability of producing a social-ready ad.
